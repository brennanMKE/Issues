# 0148 — Remove the App Sandbox (Developer-ID / DMG distribution, not App Store)

| | |
|---|---|
| **Status** | open |
| **Module** | Build / Config |
| **Platform** | macOS |
| **First seen** | 2026-06-25 |

## Description

Issues is distributed as a **code-signed, notarized Developer-ID DMG from a
website**, not through the App Store. The App Sandbox is only *required* for App
Store distribution, so it buys us nothing here — and it actively complicates
things (the CLI installer in #0147, the local `RemoteServer`, and the
security-scoped-bookmark machinery all exist to work around the sandbox).
Remove it.

Notarization does **not** require the sandbox; it requires Developer-ID signing
+ Hardened Runtime, which stay on.

## Current (contradictory) state

- `Configuration/Build.xcconfig` declares `ENABLE_APP_SANDBOX = NO` …
- … but `Issues/Issues.entitlements` ships `com.apple.security.app-sandbox =
  true`, and the **explicit entitlements file wins at signing**. Confirmed on
  the built bundle:

  ```
  $ codesign -d --entitlements :- Issues.app
    com.apple.security.app-sandbox                     = true
    com.apple.security.files.user-selected.read-write  = true
    com.apple.security.files.bookmarks.app-scope       = true
    com.apple.security.network.client                  = true
    com.apple.security.network.server                  = true
  ```

So the app is sandboxed today; the `Build.xcconfig` line is dead and
misleading. This issue makes reality match the intent.

## Why this is not just an entitlements delete

The folder-access layer is built on **security-scoped bookmarks**, which are a
sandbox-only feature. `URL.bookmarkData(options: .withSecurityScope)` requires
the `com.apple.security.files.bookmarks.app-scope` entitlement; once the sandbox
is gone, creating/resolving those bookmarks with `.withSecurityScope` fails. An
unsandboxed app can already read any file the user can, so security scope is
simply unnecessary — but the code must stop requesting it.

Call sites to convert (drop `.withSecurityScope` /
`.securityScopeAllowOnlyReadAccess` and the start/stop-access pairing; use plain
bookmarks or stored paths):

- `IssuesKit/Sources/IssuesCore/Services/FolderBookmarkService.swift` —
  create (`:92`) and resolve (`:116`, `:134`) with `.withSecurityScope`.
- `IssuesKit/Sources/IssuesCore/State/TabsModel.swift` — `:114`, `:447`, `:495`.
- `IssuesKit/Sources/IssuesCore/Services/LocalFolderIssueSource.swift` —
  `startAccessingSecurityScopedResource()` / `stop…` (`:56`, `:63`, `:83`)
  become no-ops; remove them.

## Fix

1. **Entitlements** (`Issues/Issues.entitlements`): remove the sandbox-only keys
   — `com.apple.security.app-sandbox`, `com.apple.security.files.user-selected.read-write`,
   `com.apple.security.files.bookmarks.app-scope`, and the
   `com.apple.security.network.client` / `network.server` pair (network
   restrictions only apply under the sandbox; an unsandboxed app has
   unrestricted networking, so `RemoteServer` keeps working). The file can end
   up effectively empty — keep it (or drop `CODE_SIGN_ENTITLEMENTS`) as
   convenient, but **keep Hardened Runtime on** (it's a separate build setting,
   needed for notarization).
2. **Build config**: make `Configuration/Build.xcconfig`'s `ENABLE_APP_SANDBOX =
   NO` truthful now that the entitlements agree. Confirm Hardened Runtime
   (`ENABLE_HARDENED_RUNTIME = YES`) is set for the Release/archive path.
3. **Bookmark code**: convert the call sites above to plain
   `bookmarkData(options: [])` (or just persist the folder path) and delete the
   `start/stopAccessingSecurityScopedResource` calls. Keep the
   `RememberedFolder` persistence shape and the `rememberedFolders` UserDefaults
   key so the rest of the app is unaffected.
4. **Docs**: update `CLAUDE.md` (the "App is sandboxed with read-only
   user-selected files plus app-scope bookmarks" paragraph and the entitlements
   note) to describe the unsandboxed, Developer-ID model.

## Migration note (existing users)

Remembered folders are currently security-scoped bookmarks stored in the
**sandbox container's** UserDefaults (`~/Library/Containers/co.sstools.Issues/…`).
After unsandboxing, UserDefaults reads from
`~/Library/Preferences/co.sstools.Issues.plist`, so previously-remembered
folders won't carry over and old `.withSecurityScope` bookmark data wouldn't
resolve anyway — users re-pick their folder once. Acceptable pre-1.0; mention it
in release notes. (Optional: a one-time resolve-old-then-rewrite-plain migration
if we decide it's worth it — likely not.)

## Verification

- `codesign -d --entitlements :- Issues.app` shows **no**
  `com.apple.security.app-sandbox` (and no other sandbox keys); Hardened Runtime
  still present (`codesign -d -v` / `--display` shows the `runtime` flag).
- Pick a folder, quit, relaunch → it's remembered and renders (plain bookmark
  path round-trips without security scope).
- `FolderWatcher` live-updates a user-selected folder (no security scope active).
- `RemoteServer` still serves (network works unsandboxed).
- App launches, notarizes, and passes Gatekeeper from the DMG
  (`scripts/verify-dmg.sh`) — sandbox removal doesn't affect notarization.
- Unblocks #0147: the CLI installer can use `NSAppleScript` admin escalation
  with no `apple-events` entitlement.

## Out of scope

- The CLI install feature itself — that's **#0147** (depends on this).
- Any actual networking/feature change to `RemoteServer`; this only removes the
  now-unnecessary sandbox network entitlements.
