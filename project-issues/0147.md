| | |
|---|---|

| **Module** | App / Build |
| **Platform** | macOS |

## Description

The "Install Command Line Tools…" menu item (#0136) currently can't actually
install the CLI. Because Issues.app is sandboxed, the app can't write to
`/usr/local/bin` itself, so the present `CLIInstaller` punts: it builds a
`sudo sh -c 'mkdir -p … && ln -sf …'` string, copies it to the clipboard, and
asks the user to paste it into Terminal. That's the workaround we hit problems
with — it's clunky, easy to get wrong, and not the "click Install, authorize,
done" experience.

Batty solved this properly. See **`../Batty/docs/cli-tool-install.md`**, which
documents the mechanism (modeled on the reference project **supacode**):
escalate with in-process **`NSAppleScript`** running `do shell script "…" with
administrator privileges`, which pops the standard macOS authorization dialog
(password / Touch ID), branded with the app's icon, and creates the symlink as
root. No privileged helper, no `SMJobBless`, no `osascript` subprocess.

Adopt that mechanism so `issues` (and `issues-dashboard`) install from the app
with a single auth prompt.

## Why this is the supacode case, not the Batty case

The Batty doc covers two variants. Pick the right one for Issues:

- **Batty is unsandboxed** → `do shell script … with administrator privileges`
  works with no extra entitlement.
- **supacode is sandboxed** → it works *only* because supacode carries the
  `com.apple.security.automation.apple-events` entitlement.

**Issues is sandboxed.** Verified on the built, signed bundle:

```
$ codesign -d --entitlements :- Issues.app
  com.apple.security.app-sandbox            = true
  com.apple.security.files.user-selected.read-write = true
  com.apple.security.files.bookmarks.app-scope = true
  com.apple.security.network.client/server  = true
  (no com.apple.security.automation.apple-events)
```

So Issues follows the **supacode path**: keep the sandbox (the whole
`FolderBookmarkService` app-scope-bookmark design depends on it — see
`CLAUDE.md`), and **add the `apple-events` entitlement** to let `NSAppleScript`
run under the sandbox.

> Note: `Configuration/Build.xcconfig` has a dead `ENABLE_APP_SANDBOX = NO`
> line that contradicts the entitlements file (the entitlements win at signing,
> as the `codesign` dump above proves). Reconcile that line as part of this work
> so the config stops lying about the sandbox state.

## What's already in place (don't redo)

Unlike Batty (which started from scratch), Issues already has the build/embed
half done:

- `IssuesCommand` target → `issues` binary; `DashboardCommand` target →
  `issues-dashboard` binary.
- The **"Copy CLI Tools"** copy-files phase already embeds both at
  `Issues.app/Contents/SharedSupport/bin/{issues,issues-dashboard}` (kept out of
  `Contents/MacOS/` to avoid the case-insensitive APFS clash with the `Issues`
  main executable).
- `CLIInstaller` already discovers those binaries (`bundledBinaryURLs()`) and
  targets `/usr/local/bin`.

The gap is only: the **escalation mechanism**, the **entitlement**, and an
**install-state UI**.

## Fix

### 1. Entitlement
Add to `Issues/Issues.entitlements`:

```xml
<key>com.apple.security.automation.apple-events</key>
<true/>
```

This is what lets a sandboxed app run `NSAppleScript` / `do shell script`.
Hardened Runtime stays on (required for notarization); `do shell script`
spawns a separate privileged process via the Security authorization plugin, so
no `disable-library-validation` / unsigned-memory exceptions are needed.

### 2. Rewrite `CLIInstaller`
File: `IssuesKit/Sources/IssuesAppKit/Services/CLIInstaller.swift`. Replace the
clipboard/Terminal approach with a verbatim port of supacode's installer
(`../Batty/docs/cli-tool-install.md` §2.1 / §4.3), generalized to **both**
binaries:

- `installPaths = ["/usr/local/bin/issues", "/usr/local/bin/issues-dashboard"]`,
  each symlinked to the matching `Contents/SharedSupport/bin/<name>` (keep the
  existing `bundledBinaryURLs()` source-of-truth for the in-bundle paths — do
  **not** switch to `Resources/bin`).
- `install()` builds **one** privileged command —
  `mkdir -p /usr/local/bin && rm -f <dst1> && ln -s <src1> <dst1> && rm -f <dst2> && ln -s <src2> <dst2>`
  — so the user authorizes **once** for both.
- `runPrivileged(_:prompt:)` via in-process `NSAppleScript`
  (`do shell script "…" with prompt "…" with administrator privileges`). Keep it
  in-process so the dialog shows the Issues icon/name (not Script Editor).
- `isInstalled()` → true only when **both** symlinks resolve to the current
  bundle's binary paths (`destinationOfSymbolicLink`). Moving/renaming the app
  makes it read as not-installed; re-install (`rm -f` + `ln -s`) self-heals.
- `uninstall()` → `rm -f` both symlinks, privileged, guarded by `isInstalled()`.
- `shellEscape()` single-quote wrapping on every interpolated path (bundle paths
  can contain spaces/quotes).
- Error enum: `bundledBinaryNotFound`, `cancelled` (maps NSAppleScript error
  `-128` user-cancel; `errorDescription = nil` so a cancel shows no banner),
  `installFailed(String)`.
- `NSAppleScript` is main-thread-only → call `install()/uninstall()` on the main
  actor.

### 3. Rework the UI
File: `IssuesKit/Sources/IssuesAppKit/Services/InstallCLIMenuButton.swift`
(wired in `IssuesRootScene.swift`). Drop the "copy command / open Terminal"
alert. Drive an Install / Uninstall action from `CLIInstaller` state
(`checking / installed / notInstalled / installing / uninstalling / failed`):
- On appear, call `isInstalled()` to set the initial label.
- Treat `.cancelled` as a no-op (revert state, no error).
- A small footer/help line: "Symlinks `issues` and `issues-dashboard` into
  `/usr/local/bin` so you can run them from any terminal." Keeping the menu item
  is fine; a Settings/Advanced row would also work.

## Verification

- Build + sign + (dev) run: clicking **Install Command Line Tools…** pops a
  single macOS auth dialog branded "Issues", and afterward
  `ls -l /usr/local/bin/issues /usr/local/bin/issues-dashboard` shows symlinks
  into `Issues.app/Contents/SharedSupport/bin/`.
- `issues --help` and `issues-dashboard --version` run from a fresh terminal
  (no PATH editing — `/usr/local/bin` is already on the default PATH).
- Re-running Install with the app moved to a new path repairs the now-dangling
  symlinks; `isInstalled()` flips to true again.
- Uninstall removes both symlinks under one auth prompt.
- Cancelling the auth dialog (`-128`) shows no error banner and leaves state
  unchanged.
- `codesign -d --entitlements :-` on the freshly built app shows
  `com.apple.security.automation.apple-events = true` alongside the sandbox.

## Risks / things to confirm on a signed build

- The load-bearing assumption is that a **sandboxed** Issues.app with the
  `apple-events` entitlement can run `do shell script … with administrator
  privileges` — supacode proves this, but verify on a properly **Developer-ID
  signed + notarized** build (dev-signed behavior can differ). If the
  entitlement alone proves insufficient under the sandbox, fallbacks are: (a)
  offer a no-admin `~/.local/bin` install (user-writable, but not on the default
  PATH — invasive), or (b) reconsider the sandbox. Capture the result in a
  `## Gotchas` note on resolution.
- The auth-dialog branding can't be fully verified without a signed build —
  note that when marking the issue `resolved` (per repo convention, `resolved`
  not `closed` for per-user UI work).

## Out of scope

- Dropping the sandbox entirely (would change the `FolderBookmarkService`
  app-scope-bookmark behavior — separate decision).
- A privileged helper (`SMAppService`/`SMJobBless`) — overkill for one symlink.
- CLI ↔ running-app IPC beyond what already exists (the `issues:///open?path=…`
  URL scheme); installation is orthogonal to that.
