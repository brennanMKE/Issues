# 0146 — Release tooling parity with Batty: Sparkle appcast generation + website deploy

|---|---|

## Description

Bring the Issues release pipeline up to the same shape as the proven Batty one
(`../Batty/scripts/`), so a notarized DMG can actually be published through
Sparkle and the website kept in sync. Before this, `release.sh` produced a DMG
but stopped there: the appcast had **zero `<item>` entries**, so Sparkle had
nothing to update to, and there was no script to deploy the site or sign the
update.

## What was wrong / missing

- `scripts/release.sh` used `SCHEME="Issues"`, which no longer exists (renamed
  to `Issues (Prod)` / `Issues (Beta)` in #0137). `xcodebuild archive` failed
  immediately. It also never selected the Prod variant, never injected a
  monotonic build number, and never emitted an appcast item.
- No `appcast-item.sh` — the appcast `<item>` (edSignature, length, version
  fields) was never generated from the artifact, so it could only be hand-typed
  and drift.
- No `deploy-website.sh`, `tag-release.sh`, `preflight.sh`, or `RELEASE.md`.
- `website/appcast.xml` has no `<item>` entries and there is no
  `website/downloads/` for DMG enclosures.

## What landed

- **`scripts/release.sh`** rewritten (modeled on Batty's current version):
  `set-environment.sh Prod` first → archive `Issues (Prod)` with
  `CURRENT_PROJECT_VERSION=<UTC YYYYMMDD>` → export → sign → version-consistency
  gate → DMG → notarize → staple → Gatekeeper verify → prints a ready-to-paste
  appcast `<item>`. `APP_NAME` ("Issues") is decoupled from the scheme name.
- **`scripts/appcast-item.sh`** — derives every appcast attribute from the DMG
  itself (`sign_update --account Issues`, byte length, version fields read from
  the bundle inside the mounted DMG). Enclosure → `/downloads/Issues-<X.Y.Z>.dmg`,
  release notes → `/releases/<X.Y.Z>.html`.
- **`scripts/deploy-website.sh`** — rsync `website/` to EC2 via
  `ISSUES_EC2_HOST` / `ISSUES_EC2_PATH` / `ISSUES_EC2_KEY` / `ISSUES_EC2_PORT`
  (same EC2 box as Batty).
- **`scripts/tag-release.sh`** — annotated `v<MARKETING_VERSION>` tag from
  `App.xcconfig`.
- **`scripts/preflight.sh`** — release-readiness gates (build, tests, version,
  Sparkle, signing/notary, website, working tree). Adapted: the pbxproj
  version-override gate is scoped to the app target so the existing harmless
  `IssuesUITests` `MARKETING_VERSION` lines don't false-fail; the appcast↔DMG
  gate degrades to a warning while the appcast has no items; release-notes gate
  checks `website/releases/<ver>.html`.
- **`scripts/RELEASE.md`** — end-to-end runbook.
- **`website/downloads/`** — created (with README) for DMG enclosures.

All five scripts pass `zsh -n`.

## Remaining before a real 1.0.0 ship (operator steps — not automatable here)

1. One-time: `Issues-notary` keychain profile, Developer ID cert, Sparkle key
   (`generate_keys --account Issues`), and the `ISSUES_EC2_*` env vars + remote
   docroot on the EC2 host.
2. Run `scripts/preflight.sh` and clear all `[✗]`.
3. Run `scripts/release.sh` (notarization is a shared-system action — run
   manually, not from an agent session).
4. First appcast round-trip: paste the generated `<item>` into
   `website/appcast.xml`, copy the DMG to `website/downloads/`, add
   `website/releases/1.0.0.html` notes, `deploy-website.sh`, confirm an existing
   1.0.0 build sees the update.
5. `tag-release.sh`.

## Notes

- Depends on #0145 (the Beta launch fix) being committed — `release.sh` relies
  on the Prod product being `Issues.app`.
- `SPARKLE.md` previously noted `sign_update` was intentionally not wired into
  `release.sh` for v1; that note is now superseded — generation is automated via
  `appcast-item.sh`, while the actual notarytool submission stays manual.
