# 0136 — Add menu command to install the `issues` and `issues-dashboard` CLI tools

| | |
|---|---|
| **Status** | open |
| **Module** | App / Views |
| **Platform** | macOS |
| **First seen** | 2026-05-16 |

## Description

The Issues app should expose a menu command that installs the bundled CLI tools — `issues` and `issues-dashboard` — onto the user's `PATH` so they can be invoked from a terminal. Today the CLIs are built and shipped inside the `.app` bundle (after #0134's Phase 5 reorganization) but there is no in-app affordance for putting them somewhere a shell can find them. Users have to know to symlink or copy them by hand.

The likely shape: a menu item under a top-level **Issues** or **Tools** menu — something like *Install Command Line Tools…* — that copies (or symlinks) the two binaries from the app bundle to a standard location and reports success/failure. Standard location candidates: `/usr/local/bin` (writable on Intel by default, requires authorization on Apple Silicon) or `~/.local/bin` (no-auth, but not on `PATH` by default for many users). Xcode's "Install Command Line Tools" precedent uses `/usr/local/bin` with an authorization prompt; worth mirroring.

## Steps to reproduce

1. Open Issues.app.
2. Look through the menu bar for any way to install `issues` / `issues-dashboard`.
3. Find nothing — close the app and run `which issues` in Terminal; it's not there unless you set it up manually.

## Expected behavior

A menu item (e.g. **Issues → Install Command Line Tools…**) that:

1. Locates the two CLI binaries inside the app bundle (`Contents/MacOS/issues`, `Contents/MacOS/issues-dashboard`, or wherever they actually live post-#0134).
2. Prompts the user to authorize writing to `/usr/local/bin` (or whichever destination is chosen).
3. Installs both binaries (copy or symlink — pick one and document why).
4. Shows a confirmation that includes the install path and a one-line "now you can run `issues` and `issues-dashboard` from any terminal" hint.
5. Is idempotent — re-running it overwrites the existing install cleanly.

A companion **Uninstall Command Line Tools** item would be a nice follow-up but isn't required for v1.

## Actual behavior

No menu item exists. Users must locate the binaries inside the `.app` bundle and symlink them manually.

## Notes

Design questions worth resolving before implementation:

- **Copy vs symlink.** A symlink keeps the installed `issues` pointing at whatever is inside the currently-installed `.app`, so upgrading the app upgrades the CLI for free. A copy is more robust to the app moving / being deleted but goes stale on upgrade. Xcode-style precedent is copy + replace on every upgrade.
- **Destination.** `/usr/local/bin` is the conventional answer but requires an authorization prompt (and on Apple Silicon, `/usr/local` doesn't exist by default and has to be created). `~/.local/bin` avoids the prompt but isn't on most users' `PATH`. `/opt/homebrew/bin` is owned by Homebrew and shouldn't be written to.
- **Authorization.** Use `SMAppService` / `AuthorizationServices` to elevate for the `/usr/local/bin` write. Sandboxed apps can't do this directly — confirm whether the current entitlements allow it, or whether we need a helper tool.
- **CLI binary locations post-#0134.** After Phase 5, `issues` and `issues-dashboard` are Xcode command-line tool targets that produce `.app`-less binaries. Verify where they end up in the shipped `.app` bundle — they may need to be added as bundled resources in `Contents/Resources/` or as auxiliary executables in `Contents/MacOS/`.
- **Discoverability.** A first-launch tip or onboarding card could surface this command, but that's a follow-up. The menu item alone is enough for v1.

Related: #0134 (the package move that produced the two CLI binaries in the first place), #0135 (the dashboard layout that motivates having `issues-dashboard` on `PATH`).
