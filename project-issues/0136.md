## Description

The Issues app should expose a menu command that installs the bundled CLI tools — `issues` and `issues-dashboard` — onto the user's `PATH` so they can be invoked from a terminal. Today the CLIs are built and shipped inside the `.app` bundle (after #0134's Phase 5 reorganization) but there is no in-app affordance for putting them somewhere a shell can find them. Users have to know to symlink or copy them by hand.

The likely shape: a menu item under a top-level **Issues** or **Tools** menu — something like *Install Command Line Tools…* — that copies (or symlinks) the two binaries from the app bundle to a standard location and reports success/failure. Standard location candidates: `/usr/local/bin` (writable on Intel by default, requires authorization on Apple Silicon) or `~/.local/bin` (no-auth, but not on `PATH` by default for many users). Xcode's "Install Command Line Tools" precedent uses `/usr/local/bin` with an authorization prompt; worth mirroring.

## Steps to reproduce

1. Open Issues.app.
2. Look through the menu bar for any way to install `issues` / `issues-dashboard`.
3. Find nothing — close the app and run `which issues` in Terminal; it's not there unless you set it up manually.

## Expected behavior

A menu item (e.g. **Issues → Install Command Line Tools…**) that:

1. Locates the two CLI binaries inside the app bundle (`Contents/MacOS/issues`, `Contents/MacOS/issues-dashboard`, or wherever they actually live post-#0134).
2. Prompts the user to authorize writing to `/usr/local/bin` (or whichever destination is chosen).
3. Installs both binaries (copy or symlink — pick one and document why).
4. Shows a confirmation that includes the install path and a one-line "now you can run `issues` and `issues-dashboard` from any terminal" hint.
5. Is idempotent — re-running it overwrites the existing install cleanly.

A companion **Uninstall Command Line Tools** item would be a nice follow-up but isn't required for v1.

## Actual behavior

No menu item exists. Users must locate the binaries inside the `.app` bundle and symlink them manually.

## Notes

Design questions worth resolving before implementation:

- **Copy vs symlink.** A symlink keeps the installed `issues` pointing at whatever is inside the currently-installed `.app`, so upgrading the app upgrades the CLI for free. A copy is more robust to the app moving / being deleted but goes stale on upgrade. Xcode-style precedent is copy + replace on every upgrade.
- **Destination.** `/usr/local/bin` is the conventional answer but requires an authorization prompt (and on Apple Silicon, `/usr/local` doesn't exist by default and has to be created). `~/.local/bin` avoids the prompt but isn't on most users' `PATH`. `/opt/homebrew/bin` is owned by Homebrew and shouldn't be written to.
- **Authorization.** Use `SMAppService` / `AuthorizationServices` to elevate for the `/usr/local/bin` write. Sandboxed apps can't do this directly — confirm whether the current entitlements allow it, or whether we need a helper tool.
- **CLI binary locations post-#0134.** After Phase 5, `issues` and `issues-dashboard` are Xcode command-line tool targets that produce `.app`-less binaries. Verify where they end up in the shipped `.app` bundle — they may need to be added as bundled resources in `Contents/Resources/` or as auxiliary executables in `Contents/MacOS/`.
- **Discoverability.** A first-launch tip or onboarding card could surface this command, but that's a follow-up. The menu item alone is enough for v1.

Related: #0134 (the package move that produced the two CLI binaries in the first place), #0135 (the dashboard layout that motivates having `issues-dashboard` on `PATH`).

## Root cause

Feature was missing — the two CLI tool targets (`IssuesCommand` / `DashboardCommand`) existed after #0134 but the Issues app target had no dependency on them and no Copy Files build phase to embed them in `Issues.app/Contents/MacOS/`, and there was no menu affordance to put them onto the user's `PATH`.

## Fix

- Made the `Issues` app target depend on the `IssuesCommand` and `DashboardCommand` tool targets and added a Copy Files build phase (`dstSubfolderSpec = 6`, "Executables") that bundles the produced `issues` and `issues-dashboard` binaries into `Issues.app/Contents/MacOS/` next to the main executable. Verified by inspecting the built bundle.
- Added a new menu item `Install Command Line Tools…` under the existing **Issues** app-menu group (`CommandGroup(after: .appInfo)`), next to `Check for Updates…`.
- Added `CLIInstaller` (a `nonisolated` enum) that resolves the two bundle binaries, builds a `mkdir -p /usr/local/bin && ln -sf … && ln -sf …` command, and runs it via `osascript -e 'do shell script "…" with administrator privileges'`. `ln -sf` keeps the operation idempotent and a symlink (vs. a copy) lets app upgrades automatically refresh the installed CLI.
- Added `InstallCLIMenuButton`, a small SwiftUI view (mirrors `HelpMenuButton`) that owns the in-flight state, dispatches the install to a detached `Task`, and presents an `NSAlert` with the outcome.
- Sandbox fallback: if the elevated `osascript` invocation fails (which it can under the app sandbox), the installer writes `~/Downloads/install-issues-cli.sh` and the alert offers a *Reveal in Finder* button so the user can run it with `sudo sh …`.

## Files changed

- `Issues.xcodeproj/project.pbxproj` — new target dependencies, new `Copy CLI Tools` build phase on the Issues target, build-file entries for the two bundled CLI binaries.
- `IssuesKit/Sources/IssuesAppKit/IssuesRootScene.swift` — added `InstallCLIMenuButton()` to the `CommandGroup(after: .appInfo)` group.
- `IssuesKit/Sources/IssuesAppKit/Services/CLIInstaller.swift` — new file. The installer service (osascript invocation, shell-quoting, fallback script writer).
- `IssuesKit/Sources/IssuesAppKit/Services/InstallCLIMenuButton.swift` — new file. SwiftUI menu-item view and `NSAlert` presenter.

## Gotchas

- **Decisions taken (per #0136 Notes):** symlink (not copy), `/usr/local/bin` (not `~/.local/bin`), authorization via `osascript … with administrator privileges` (not SMJobBless / privileged helper).
- **CLI binaries were not bundled before.** The `IssuesCommand` and `DashboardCommand` targets exist post-#0134 but the `Issues` scheme didn't depend on them; their products landed in `BUILT_PRODUCTS_DIR` but never inside `Issues.app`. Adding the target dependencies plus a Copy Files phase (`dstSubfolderSpec = 6` — "Executables", which maps to `Contents/MacOS/` for an app wrapper) embeds them next to the main executable. The two pre-existing `CopyFiles` phases on each CLI target (originally pointing at `/usr/share/man/man1/`) are unrelated and left as-is.
- **Sandbox + osascript.** The app keeps `com.apple.security.app-sandbox = true`. Spawning `osascript` from a sandboxed app can be blocked by macOS. The fallback path (write a shell script, reveal in Finder, user runs `sudo sh …`) keeps the sandbox intact while still giving the user a one-click path forward. A fully automated experience would require disabling the sandbox or shipping a SMAppService helper tool — both judged out of scope.
- **Swift 6 isolation.** The package compiles with `-default-isolation MainActor`. `CLIInstaller` is marked `nonisolated` so its `static func install()` can be called from a `Task.detached` without crossing the main actor.
- **Symbolic-link path lifetime.** A symlink in `/usr/local/bin` points at the *current* bundle location. If the user moves `Issues.app` (e.g. trashes a downloaded copy after copying to `/Applications`), the symlink goes stale and the user should re-run *Install Command Line Tools…*.
- **macOS permissions panel.** First run triggers the standard authentication panel (osascript). No automation-permission prompt is expected because osascript is invoking `/bin/sh`, not scripting another app.
