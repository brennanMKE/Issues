## Description

`FolderWatcher` (FSEvents + 150 ms debounce) and `FolderBookmarkService` (security-scoped bookmarks persisted in `UserDefaults`) are the two pieces of infrastructure the app depends on for live data. The watcher fires on any directory change; the parser filters to `^\d{4}\.md$` files only. Both have zero UI test coverage. A broken debounce, a mis-wired FSEvents callback, or a stale bookmark would be invisible until the user noticed the app had gone stale. This suite asserts the end-to-end live-reload loop and the bookmark persistence boundary.

## Regressions this suite would have caught

- **Debounce mis-wiring** (latent) — If the `FolderWatcher.Session` callback were accidentally disconnected from `IssueStore.reload()`, no issue file change would ever update the UI. A test that writes a file and asserts the new cell appears would fail immediately.
- **Non-issue file contamination** (latent) — If the `^\d{4}\.md$` filename gate were removed, files like `Issues.md` or `project.json` would attempt to parse as issues and likely produce malformed entries or a crash. A test writing non-matching files and asserting the issue count does not change locks in the gate.
- **Bookmark staleness recovery** (latent) — If `FolderBookmarkService` returned a stale bookmark after a folder was moved and the app didn't surface the "Locate folder…" recovery path, the user would see a frozen list with no error. A test simulating a stale bookmark and asserting the recovery UI appears would lock this in.
- **Double-reload on burst writes** (latent) — Writing 3 files in quick succession should produce one reload (debounce collapses them), not 3. A test writing a burst and asserting the issue count reaches the expected final value after the debounce window — without intermediate intermediate states — guards against debounce removal or timer mis-configuration.

## Test cases

All tests use the foundation from #0139. The harness's `folderURL` is a plain temp directory; `ISSUES_UI_TEST_FOLDER` bypasses the bookmark layer so the watcher tests focus on FSEvents → debounce → reload.

### File addition

- **Adding a new issue file causes the cell to appear.** Launch with the standard 6 fixtures. Call `harness.writeIssue(id: 10, …)`. Wait up to 2 seconds. Assert `issue-cell.0010` exists and total cell count is 7.
- **Adding a non-matching file (e.g. `Notes.md`) does not change the issue list.** Write `Notes.md` to the folder. Wait 2 seconds. Assert issue count is still 6. This locks in the `^\d{4}\.md$` filename gate.
- **Adding a subdirectory does not change the issue list.** Create a subdirectory inside the folder. Wait 2 seconds. Assert count is still 6 (subdirectory contents are not recursed into by the watcher or the parser).

### File modification

- **Changing an issue's status field updates the existing cell.** Call `harness.modifyIssueStatus(id: 1, to: "in-progress")`. Wait up to 2 seconds. Assert `issue-cell.0001.status` accessibilityValue is now `"in-progress"`. Assert total cell count is unchanged (still 6).
- **Changing an issue's title updates the cell's displayed title.** Rewrite 0001's first line with a new title. Assert the new title appears in `issue-cell.0001.title` or the detail panel after reselection.

### File deletion

- **Deleting an issue file removes the cell.** Call `harness.deleteIssue(id: 1)`. Wait up to 2 seconds. Assert `issue-cell.0001` does not exist. Assert total cell count is 5. Assert `stats-bar.count.open` decreased by 1 (0001 was open).
- **Deleting the selected issue collapses the detail panel.** Select `issue-cell.0001`. Delete it via the harness. Assert `detail-panel.root` disappears within 2 seconds.

### Burst-write debounce

- **Writing 5 files in rapid succession produces one reload, not 5.** Write 5 issue files without any sleep between them. Wait for the debounce window (300 ms). Assert the final cell count is 11 (6 fixtures + 5 new). Assert no intermediate partially-loaded state was visible (the approach: assert count goes from 6 to 11 without ever reading 7, 8, 9, or 10 — achievable by polling after the debounce settles rather than during).

### Filename gate (non-issue files)

- **`project.json` is not parsed as an issue.** Write a valid `project.json` to the folder. Assert issue count does not change.
- **`Issues.md` is not parsed as an issue.** Same assertion.
- **`0001.txt` (wrong extension) is not parsed.** Same assertion.
- **`10001.md` (5 digits) is not parsed.** Same assertion. (The gate is `^\d{4}\.md$` — exactly 4 digits.)

### Bookmark persistence (requires a real sandbox-aware test path)

The `FolderBookmarkService` path cannot be fully exercised with `ISSUES_UI_TEST_FOLDER` (which bypasses it). These tests launch without the env var and interact with the folder picker directly.

- **Picking a folder persists the bookmark; the folder reloads on relaunch.** Use `folder-picker.root` to open a real folder via the open-panel. Terminate and relaunch without the env var. Assert `main-view.root` appears immediately (no picker shown) and the previously loaded issues are visible.
- **Stale bookmark surfaces the recovery path.** Set up a bookmark, then move the folder to a different path between launches (the harness can do this). Relaunch. Assert the app shows a "Locate folder…" button or equivalent error element rather than an empty/frozen list.

## Accessibility identifiers needed (from #0139)

- `issue-cell.<id>` — covered.
- `issue-cell.<id>.status` — covered.
- `issue-cell.<id>.title` — **new** (listed in #0139 inventory; verify it's added).
- `detail-panel.root` — covered.
- `stats-bar.count.<status>` — covered.
- `folder-picker.root` — covered.
- `main-view.root` — covered.
- `folder-picker.locate-folder` — **new**, needed for the stale-bookmark recovery test.

## Out of scope

- The internal FSEvents stream parameters (latency, flags). Those are implementation details of the `Watcher` package; trust the package's own tests.
- Remote folder watching (tracked in #0076 series — the remote `IssueSource` protocol replaces the local watcher for remote tabs).
- Watching multiple folders simultaneously (multi-tab is tracked in #0002; this suite covers the single-folder path only).

## Acceptance criteria

- All test cases pass under `xcodebuild -scheme 'Issues (Beta)' -destination 'platform=macOS' test`.
- All file-mutation tests use `waitForExistence(timeout: 2.0)` — not bare `XCTAssert` — to absorb the debounce.
- The burst-write test asserts on the *final* count, not intermediate states, so it doesn't become a timing-dependent flake.
- The bookmark tests are in a separate `IssuesBookmarkUITests` class or clearly separated group so they can be run or skipped independently (they are slower and require the folder picker UI).

## Notes

- Depends on #0139.
- The 150 ms debounce is configured in `FolderWatcher`. Tests use a 2 second `waitForExistence` timeout — 13× the debounce — for headless CI headroom without making tests unbearably slow.
- `harness.writeIssue(…)` uses `FileManager` to write atomically (write to a temp file, then `moveItem(atPath:toPath:)`) to avoid the watcher seeing a half-written file. Document this in `IssuesUITestHarness`.
- The stale-bookmark test is the trickiest to implement: it requires moving a directory between process launches, which the harness can do by creating the folder under one name, recording the path, and renaming it before the second launch. Keep this in a separate test class so setup/teardown complexity stays isolated.
