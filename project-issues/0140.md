## Description

The filter system (status, module, platform) and the stats bar have no automated test coverage. The filtering rules include a non-obvious edge case — an issue with `platform = All` matches every platform filter value — and the stats bar must compute from the *unfiltered* list regardless of the active filter combination. Both of these semantics have stable documented behavior that should be locked in with tests before any refactor of `IssueStore`.

## Regressions this suite would have caught

- **#0068** — Option-click on a single status filter inverts the selection. Any test asserting the filter toggle behavior from a known state would have caught a change in click semantics.
- **Stats bar drift** (latent) — If the stats bar computation were accidentally switched to the filtered list, every filter interaction would produce wrong counts. No test currently catches this.
- **Platform "All" short-circuit** (latent) — The `issue.platform != "All"` guard in the filter predicate is the only place `"All"` is special. A refactor that normalizes platform values or changes the predicate order silently breaks it.
- **Filter combination** (latent) — Status + module + platform filters are ANDed. A test for combinations guards against `||` / `&&` bugs in the predicate.

## Test cases

All tests use the foundation from #0139 — `IssuesUITestHarness` with the standard fixture set.

### Status filter

- **Selecting `open` shows only open issues.** Tap `filter.status.open`. Assert `issue-cell.0001` exists, `issue-cell.0002` does not (in-progress), `issue-cell.0003` does not (resolved).
- **Selecting `in-progress` shows only in-progress issues.** Tap `filter.status.in-progress`. Assert only `issue-cell.0002` exists.
- **Tapping the active filter again clears it.** Select `open`, then tap `open` again. Assert all 6 fixture issues are visible.
- **Stats bar does not change when a status filter is applied.** Record `stats-bar.count.open` accessibilityValue before and after applying `filter.status.in-progress`. Assert the value is unchanged.

### Module filter

- **Selecting `Views` shows only Views-module issues.** Tap `filter.module.Views`. Assert `issue-cell.0001` (Views/open), `issue-cell.0003` (Views/resolved), `issue-cell.0005` (Views/All) exist; `issue-cell.0002` (Services) does not.
- **Selecting a module with no issues shows an empty list.** Add a module filter value not present in the fixture set. Assert no `issue-cell.*` elements exist.

### Platform filter

- **Selecting `macOS` excludes iOS issues but includes `All` issues.** Tap `filter.platform.macOS`. Assert `issue-cell.0004` (iOS) is absent. Assert `issue-cell.0005` (All) is present — this is the `"All"` short-circuit regression test.
- **Selecting `iOS` shows iOS and All issues.** Tap `filter.platform.iOS`. Assert `issue-cell.0004` exists and `issue-cell.0005` exists. Assert `issue-cell.0001` (macOS) does not.
- **Selecting `All` as a filter value shows every issue.** If the UI exposes `All` as a filter chip, assert every fixture issue is visible. This confirms `All` is treated as "no platform restriction" not "filter to issues whose platform field is literally All".

### Filter combination

- **Status + module filter is AND, not OR.** Apply `filter.status.open` and `filter.module.Views`. Assert only `issue-cell.0001` is visible (open AND Views); `issue-cell.0003` (resolved/Views), `issue-cell.0002` (in-progress/Services) are absent.
- **Adding a third filter (platform) further narrows results.** Status=open, module=Views, platform=macOS. Assert `issue-cell.0001` (open/Views/macOS) exists; `issue-cell.0005` (open/Views/All) also exists (the `All` short-circuit). Assert `issue-cell.0004` (open/State/iOS) does not.

### Stats bar accuracy

- **Stats bar counts match unfiltered totals.** With no filter active, record counts for every status bucket. Apply multiple filters. Re-read every bucket. Assert all counts are identical before and after filtering.
- **Stats bar updates when a file is added or deleted.** Add a new `open` issue via `harness.writeIssue(…)`. Wait for debounce. Assert `stats-bar.count.open` increased by 1. Delete the issue. Assert it returns to the original count.

### Filter clear

- **`filter.clear` removes all active filters and restores all issues.** Apply status + module + platform filters. Tap `filter.clear`. Assert all 6 fixture issues are visible.

## Out of scope

- The visual appearance of selected vs. unselected filter chips.
- Persistence of filter state across launches (#0009 tracks per-tab filter memory; no test here until that feature lands).
- Filter interactions with view modes (tested in #0141).

## Acceptance criteria

- All test cases pass under `xcodebuild -scheme 'Issues (Beta)' -destination 'platform=macOS' test`.
- Each test comment names the regression or invariant it covers.
- The `"All"` platform short-circuit test is explicitly named `testPlatformFilterIncludesAllPlatformIssues` so it is obviously a regression guard.
- Stats bar tests use a fresh harness (no filter state leak between test methods).

## Notes

- Depends on #0139 for the harness and accessibility identifiers.
- The filtering rules are encoded verbatim in `IssueStore.swift` (the `CLAUDE.md` "must stay exact" block). Tests here lock them in — if the predicate changes, tests fail, and the developer has to consciously update both.
- Stats bar timing: `stats-bar.count.*` must update synchronously with the reload (they're part of the same `@Observable` pass). No extra wait needed beyond the debounce for file-mutation tests.
