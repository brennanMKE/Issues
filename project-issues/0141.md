# 0141 — UI test suite: view mode switching (swimlane, timeline, list, recent)

| | |
|---|---|
| **Status** | open |
| **Module** | Tests / Views |
| **Platform** | macOS |
| **First seen** | 2026-05-24 |

## Description

The four view modes (swimlane, timeline, list, recent) are independent rendering paths that share the same `IssueStore` state but produce different layouts. Mode switching is a one-line change to `IssueStore.viewMode`, but the *rendering* of each mode has its own bugs (#0066 view-mode label wrapping). None of the four modes is covered by UI tests. This suite asserts that each mode renders the expected set of issues from the standard fixture and that switching modes does not corrupt selection or filter state.

## Regressions this suite would have caught

- **#0066** — View-mode segment control labels wrapped when the window was narrow. A test asserting `view-mode.<mode>` elements are all hit-testable at a constrained window width would have caught the layout break.
- **Issue count consistency** (latent) — If a mode accidentally filtered issues (e.g. recent view silently dropping `resolved` status issues), no test would catch it. Each mode should show every issue that passes the active filter, regardless of mode.
- **Selection persistence** (latent) — If switching view modes cleared `selectedIssueID` unexpectedly, `detail-panel.root` would disappear. That's observable but untested.

## Test cases

All tests use the foundation from #0139 — `IssuesUITestHarness` with the standard fixture set (6 issues, mixed statuses, modules, platforms).

### Mode switching — basic reachability

- **All four mode buttons are hittable at default window size.** After launch, assert `view-mode.swimlane`, `view-mode.timeline`, `view-mode.list`, `view-mode.recent` all exist and are `isHittable`.
- **All four mode buttons are hittable at a narrow window width.** Resize the window to 700 pt wide. Re-assert all four elements are hittable. This is the #0066 regression test.

### Issue count per mode

For each mode (run as parameterized or repeated test):

- **Each mode shows all 6 fixture issues.** Switch to the mode. Assert exactly 6 `issue-cell.*` elements exist.
- **After applying a status filter, each mode shows the same filtered count.** Apply `filter.status.open` (3 open issues in the fixture set: 0001, 0004, 0005). Switch through all four modes. Assert exactly 3 `issue-cell.*` elements in each mode.

### Selection persistence across mode switch

- **Selecting an issue then switching mode keeps the detail panel open.** In List view, tap `issue-cell.0001`. Assert `detail-panel.root` exists. Switch to Timeline. Assert `detail-panel.root` still exists with `detail-panel.title` matching issue 0001's title.
- **Switching mode does not change the selected issue.** Select 0001 in Swimlane. Switch to List. Assert `detail-panel.title` still reflects 0001, not a different issue.
- **Switching mode with no selection keeps no selection.** Without selecting an issue, switch through all modes. Assert `detail-panel.root` does not exist in any mode.

### Recent view semantics

- **Recent view shows issues sorted by last-modified time.** Use `harness.modifyIssueStatus(id: 3, to: "closed")` to touch issue 0003's file. Switch to Recent. Assert `issue-cell.0003` appears first (or near-first) in the list.
- **Recent view excludes no issues based on status.** Assert all 6 fixture issues appear (recent is a sort, not a filter).

### Mode state indicator

- **Active mode is indicated as selected.** After switching to Timeline, assert `view-mode.timeline` has `accessibilityValue == "selected"` and `view-mode.list` has `accessibilityValue == "unselected"`.

## Accessibility identifiers needed (from #0139)

- `view-mode.picker` — the segmented control.
- `view-mode.<mode>` — `swimlane`, `timeline`, `list`, `recent`.
- `issue-cell.<id>` — covered.
- `detail-panel.root` — covered.
- `detail-panel.title` — covered.

## Out of scope

- The visual layout *within* each mode (swimlane column widths, timeline bar proportions, list row heights). Those are snapshot territory.
- Scroll position after mode switch (no regression history; add if a bug surfaces).
- The `recent` view's age-display formatting (#0064 and related — separate feature).

## Acceptance criteria

- All test cases pass under `xcodebuild -scheme 'Issues (Beta)' -destination 'platform=macOS' test`.
- The narrow-window test uses a window width small enough to reproduce the #0066 wrapping (700 pt is a safe lower bound).
- Each test uses a fresh harness and fresh app launch so mode state doesn't bleed between methods.
- The recent-view sort test uses `waitForExistence(timeout: 2.0)` after the file mutation to absorb the debounce.

## Notes

- Depends on #0139.
- The parameterized-test approach (one helper that accepts a mode name and runs assertions for all four modes) keeps the mode-switching tests DRY. Swift's `XCTest` doesn't have first-class parameterization; use a private helper method called four times or a loop over an array.
- If the recent view applies any implicit filter (e.g. only showing issues modified in the last N days), that behavior must be documented and tested explicitly — right now the app has no such filter, but the test that asserts all 6 issues appear will fail if one is ever added silently.
