## Description

The existing `IssuesUITests` target is the Xcode-generated stub — `testExample()` and `testLaunchPerformance()`, nothing else. The filter, view mode, detail panel, and folder watching paths have all produced bugs (#0040, #0041, #0066, #0068, #0072) that were caught by manual inspection only. This issue builds the foundation that the area-specific test suites (#0140–#0143) depend on: a way to point the app at a known test folder without going through the folder picker, and the accessibility identifiers needed to drive and assert on every major surface.

## Why a test folder instead of an intent driver

Issues.app is file-driven. The entire data flow is `folder → MarkdownIssueParser → IssueStore → views`. There is no in-process state-mutation surface analogous to Batty's `AppStateStore` intent dispatcher. The correct test driver is:

1. **Write known fixture files** to a temp directory before launch.
2. **Pass the path** via a launch-argument so the app loads that folder instead of showing the folder picker.
3. **Mutate files at runtime** (add/delete/modify `.md` files in the temp dir) to exercise the folder-watcher path.
4. **Assert on accessibility identifiers** after the 150 ms debounce settles.

This is simpler than an intent dispatcher and stays honest to the app's actual architecture.

## Part 1 — Launch-arg test folder

### Surface

App reads `ISSUES_UI_TEST_FOLDER` env var early in `IssueStore` initialization (or at the app entry point alongside the existing sandbox setup). When set, the value is treated as a plain file URL and passed directly to `IssueStore.start()`, bypassing `FolderBookmarkService` entirely. The folder picker view is suppressed — `RootView` shows `MainView` immediately.

The test folder is a plain temp directory (`FileManager.default.temporaryDirectory`); no security-scoped bookmark is needed because the sandbox allows unrestricted access to `$TMPDIR`.

### Harness

New file `IssuesUITests/IssuesUITestHarness.swift`:

```swift
final class IssuesUITestHarness {
    let folderURL: URL

    init() {
        folderURL = FileManager.default.temporaryDirectory
            .appending(path: "IssuesUITestFixtures-\(UUID().uuidString)")
        try! FileManager.default.createDirectory(at: folderURL, withIntermediateDirectories: true)
    }

    func launch() -> XCUIApplication {
        let app = XCUIApplication()
        app.launchEnvironment["ISSUES_UI_TEST_FOLDER"] = folderURL.path
        app.launch()
        return app
    }

    func writeIssue(id: Int, title: String, status: String, module: String, platform: String = "macOS") {
        // Writes a minimal NNNN.md to folderURL
    }

    func deleteIssue(id: Int) { … }

    func modifyIssueStatus(id: Int, to status: String) { … }

    func tearDown() {
        try? FileManager.default.removeItem(at: folderURL)
    }
}
```

The harness writes `.md` files using the canonical format (em-dash title, bold metadata rows, `YYYY-MM-DD` date). `writeIssue` and friends are the only place the format is encoded in the test target — a format change breaks one place.

## Part 2 — Accessibility identifier inventory

Add identifiers to every surface that tests need to assert on. Identifiers use kebab-case with structural suffixes where natural.

### Root / navigation

| Identifier | View | Notes |
|---|---|---|
| `folder-picker.root` | `FolderPickerView` | Present when no folder is loaded |
| `main-view.root` | `MainView` | Present when a folder is loaded |
| `stats-bar.root` | `StatsBarView` | Always present inside `MainView` |
| `toolbar.root` | `ToolbarView` | Always present inside `MainView` |

### Stats bar

| Identifier | Notes |
|---|---|
| `stats-bar.count.<status>` | One element per status bucket (`open`, `in-progress`, `resolved`, `closed`, `wontfix`). `accessibilityValue` = integer count as string. |

### Filters

| Identifier | Notes |
|---|---|
| `filter.status.<value>` | One button per status filter value. `accessibilityValue` = `"selected"` / `"unselected"`. |
| `filter.module.<value>` | One button (or picker row) per module. |
| `filter.platform.<value>` | One button per platform value. |
| `filter.clear` | The "clear all filters" action. |

### View mode

| Identifier | Notes |
|---|---|
| `view-mode.picker` | The segmented control or picker. |
| `view-mode.<mode>` | One element per mode: `swimlane`, `timeline`, `list`, `recent`. `accessibilityValue` = `"selected"` / `"unselected"`. |

### Issue cells (all view modes)

| Identifier | Notes |
|---|---|
| `issue-cell.<id>` | One element per visible issue. `id` is the 4-digit zero-padded number. |
| `issue-cell.<id>.title` | The title text within the cell. |
| `issue-cell.<id>.status` | The status badge within the cell. `accessibilityValue` = status string. |

### Detail panel

| Identifier | Notes |
|---|---|
| `detail-panel.root` | Present when an issue is selected. |
| `detail-panel.title` | The issue title in the panel. |
| `detail-panel.status` | The status shown in the panel. |
| `detail-panel.description` | The description/body text area. |
| `detail-panel.close` | The close/deselect button if one exists. |

## Acceptance criteria

- `ISSUES_UI_TEST_FOLDER` env var causes the app to load directly into `MainView` using that folder as the source, bypassing `FolderPickerView` and `FolderBookmarkService`.
- `IssuesUITestHarness.launch()` returns a running `XCUIApplication` with the fixture folder loaded.
- `IssuesUITestHarness.writeIssue(…)` adds a file and, after the debounce window (≤ 300 ms), the new `issue-cell.<id>` appears in the UI.
- All identifiers in the inventory above are present on their corresponding views.
- A smoke test verifies the standard fixture set produces exactly 6 `issue-cell.*` elements in List view.

## Implementation notes

- Gate the `ISSUES_UI_TEST_FOLDER` path on the env var at runtime (not `#if DEBUG`). UI tests run against the Beta build which is not a debug build.
- `FolderBookmarkService` is not modified — the test path bypasses it entirely. This keeps the production bookmark flow untouched.
- The 150 ms debounce means every assertion after a file mutation needs `waitForExistence(timeout: 2.0)` or similar. Document this clearly in `IssuesUITestHarness` so future test authors don't write racy `XCTAssert`s.
- This issue blocks #0140–#0143. The area suites can have their test cases drafted in parallel — the harness is the only path-clearing work.

## Notes

- Unlike Batty, there is no intent dispatcher to implement. The driver is entirely file I/O + XCUITest element actions. This makes the foundation simpler to build but means test setup is slightly slower (file writes + debounce vs. synchronous in-process dispatch).
- The `ISSUES_UI_TEST_FOLDER` path should be logged via the `co.sstools.Issues` logger subsystem at `debug` level on startup so test failures are diagnosable from Console.app.
